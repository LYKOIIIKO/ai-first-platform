# Технический каркас платформы и локальное окружение

Статус: спецификация согласована. Владелец подтвердил уровни проверок по процессу to-spec.

Опубликовано: [GitHub issue #1](https://github.com/LYKOIIIKO/ai-first-platform/issues/1), метка ready-for-agent. Опубликованный текст проверен; эта ссылка добавлена в локальную копию после публикации.

## Problem Statement

Владелец начинает учебный проект и хочет изучить новые технологии на реальной архитектуре платформы. В репозитории уже согласованы требования, термины, предметная модель и технические решения. Исполняемых приложений и локального окружения пока нет.

Без общего каркаса нельзя проверить соединение интерфейса, backend и базы. Нельзя автоматически обнаружить нарушения границ модулей. Разные настройки компьютеров также могут мешать повторяемому запуску.

Нужна минимальная техническая основа для последующей реализации первой версии. На этом этапе пользовательские функции не реализуются.

## Solution

Подготовить единый репозиторий с отдельными frontend и backend и общими командами. Запускать web, API, PostgreSQL и RabbitMQ через Docker Compose. Обеспечить обновление исходников, проверки готовности и безопасные локальные настройки.

Зафиксировать границы пяти предметных модулей и структуру frontend по FSD. Настроить автоматические проверки импортов локально и для pull request. Добавить техническую страницу `/system` для проверки HTTP-контракта и готовности окружения.

## Implementation Decisions

- Цель задачи — реализовать согласованный технический каркас. Учебная ценность важнее минимального времени разработки.
- Backend: Node.js, TypeScript и NestJS с HTTP-адаптером Fastify. Совместимые версии NestJS и адаптера закрепляются при подготовке каркаса. Frontend: React, TypeScript и Vite. База: PostgreSQL. Доступ к базе: Drizzle ORM, SQL-миграции через Drizzle Kit.
- Ветки среды: Node.js 24 LTS, PostgreSQL 18, RabbitMQ 4 и pnpm 12. Точные совместимые версии закрепляются при реализации. Не подменять согласованные ветки молча, если обнаружится проблема доступности или совместимости.
- Репозиторий объединяет два приложения в pnpm workspace. Каждое приложение имеет собственные зависимости и команды. Из корня доступны общие команды установки, запуска и проверок. Используется общий lock-файл.
- Общие пакеты появляются при наличии реального общего кода. Пустые пакеты для предполагаемых будущих потребностей не создавать.
- Backend — модульный монолит. Пять предметных модулей: «Сотрудники», «Проекты», «Доступ», «Подключения агентов» и «Интеграции».
- «Сотрудники» отвечают за приглашения, учётные записи, вход через GitHub, состояние и роль. «Проекты» отвечают за состав проектов, репозитории и инструкции.
- «Доступ» отвечает за назначения, требуемые права и сверку прав. «Подключения агентов» отвечают за действительность подключений Codex. «Интеграции» выполняют операции с внешними сервисами от имени компании.
- Эта ответственность задаёт границы будущей реализации. Данная задача создаёт точки входа модулей, но не реализует перечисленные пользовательские операции.
- У предметного модуля две открытые точки входа: контракт и сборка NestJS. Внутренние файлы, включая описания таблиц, закрыты для других модулей.
- Обычный межмодульный код импортирует только `public.ts` и соблюдает граф разрешённых зависимостей. Файлы `*.module.ts` используются при сборке NestJS.
- Каждая будущая таблица принадлежит одному модулю. Другие модули обращаются к владельцу через его интерфейс. Прямое чтение или изменение чужих таблиц запрещено.
- Каждый предметный модуль использует свою схему внутри общей базы PostgreSQL. Схема создаётся вместе с первой таблицей модуля. Правило для внешних ключей между схемами определяется при проектировании первого назначения проекта.
- Типы строк и вставок выводятся из описаний Drizzle. Повторные ручные описания тех же полей не требуются. Предметные таблицы в этой задаче не создаются.
- Drizzle Kit ведёт одну общую историю SQL-миграций для всех схем. С первой предметной миграцией Compose получает одноразовый сервис `migrate`. Он применяет миграции после готовности PostgreSQL. Успешное завершение сервиса требуется до запуска API.
- С первой предметной миграцией используются две роли PostgreSQL. Роль миграций меняет структуру базы. Роль API читает и записывает данные в пределах выданных прав и не может менять структуру. Учётные данные роли миграций получает только сервис `migrate`.
- Для чтения актуального состояния и решений в рамках запроса модули используют прямые вызовы интерфейсов. RabbitMQ доставляет события для фоновых последствий изменений.
- Первое предметное событие — отключение сотрудника. «Сотрудники» сохраняют новое состояние и событие в одной транзакции PostgreSQL (transactional outbox). После сохранения событие доставляется через RabbitMQ в отдельные очереди «Доступа» и «Подключений агентов». Обработчики подтверждают сообщение после сохранения своего результата и безопасно обрабатывают повторную доставку. Платформа блокирует новые запросы по текущему состоянию учётной записи сразу после его изменения.
- Сквозные действия координирует прикладной слой над предметными модулями. Он не дублирует предметные правила. В этой задаче будущие сценарии и их методы не создаются.
- Прикладные сценарии могут обращаться к любому необходимому предметному модулю. Предметные модули не вызывают прикладные сценарии.
- «Доступ» может зависеть от «Сотрудников», «Проектов» и «Интеграций». «Подключения агентов» могут зависеть от «Сотрудников».
- «Сотрудники», «Проекты» и «Интеграции» не зависят от других предметных модулей. Остальные предметные зависимости запрещены. Общая техническая инфраструктура не считается дополнительным предметным модулем.
- Ответственность за повторы и актуальность сверок остаётся у «Доступа». «Интеграции» выполняют одну попытку сверки. Технический каркас не переносит эту ответственность в прикладной слой.
- Отдельно размещаются запуск backend, сборка NestJS, прикладной слой, предметные модули, транспорт и техническая инфраструктура. Не создавать методы, классы и внутренние каталоги будущих операций.
- Входной слой (Edge) размещается внутри `apps/api/src/transport`. Он обрабатывает общие проверки защищённых запросов. Для web он проверяет сессию через «Сотрудников», для Codex — действительность подключения через «Подключения агентов». Он проверяет актуальное состояние учётной записи через «Сотрудников». Только после успешных проверок Edge передаёт прикладному сценарию подтверждённые идентификаторы сотрудника и, для Codex, подключения.
- Прикладной сценарий получает решение о правах на проект у модуля «Доступ». Перед началом отправки ответа Codex сценарий повторно проверяет доступность выдаваемых сведений и исключает сведения с отозванным доступом.
- В каркасе фиксируются место и ответственность Edge. Проверка сессии появляется с первым защищённым веб-запросом. Проверка подключения появляется с первым защищённым входом для Codex.
- Frontend использует FSD. Предусмотрены слои app, pages, widgets, features, entities и shared. Они появляются по необходимости; для каркаса достаточно реально используемых частей.
- Для UI выбран [SmoothUI](https://github.com/educlopez/smoothui). Tailwind CSS — единственный способ стилизации компонентов SmoothUI и собственных компонентов. С первым рабочим интерфейсом подключаем Tailwind CSS и добавляем нужные компоненты SmoothUI со штатными стилями. При копировании исходников сохраняем уведомления лицензии.
- TanStack Router и TanStack Query подключаются в каркасе для страницы `/system`. Файловые маршруты размещаются в `app` и подключают страницы из `pages`. React Hook Form и Zod на frontend подключаются с первой пользовательской формой.
- Слайсы используют нижележащие слои через открытые точки входа с именованными экспортами. Связи слайсов одного слоя по умолчанию запрещены. Внутренние файлы не импортируют собственную открытую точку входа.
- App и Shared состоят из сегментов без слайсов. Связи между сегментами внутри этих слоёв разрешены. Для Shared открытые точки входа определяются по сегменту или отдельной библиотеке либо компоненту.
- Специальные связи сущностей FSD через @x требуют отдельной реальной потребности. В каркасе такие исключения не вводятся.
- Frontend обращается к backend по HTTP. Импорты серверных исходников и описаний Drizzle из frontend запрещены.
- Backend описывает HTTP-данные схемами Zod. В каркасе схемы описывают тела ответов `GET /health/ready` для HTTP 200 и 503. Из описания маршрута и схем генерируется OpenAPI. Frontend использует типы, сгенерированные через `openapi-typescript`, и HTTP-клиент `openapi-fetch`.
- Документ OpenAPI и сгенерированные типы хранятся в Git. Команда генерации работает без запущенных PostgreSQL и RabbitMQ. На pull request CI повторно генерирует оба файла и завершает проверку с ошибкой при расхождении с сохранёнными версиями.
- Dependency-cruiser проверяет матрицу зависимостей, открытые точки входа и циклы. Разрешение импортов учитывает настройки TypeScript. Импорты типов подчиняются тем же правилам.
- ESLint no-restricted-imports даёт раннюю обратную связь для простых запретов, включая доступ к чужим внутренним файлам. Полную матрицу не дублировать вручную в двух конфигурациях.
- Сообщение об ошибке показывает запрещённый импорт и нарушенное правило. Если правило допускает другую точку входа, сообщение подсказывает её. Например, для допустимого межмодульного вызова используется `public.ts`.
- Правила охватывают backend и согласованные границы FSD. Нарушение завершает проверку с ошибкой локально и при проверке pull request в GitHub.
- Предметный код не импортирует NestJS, Drizzle, клиент RabbitMQ и транспорт. Правило проверяется при появлении первого кода с предметными правилами. Пустые каталоги под него не создаются.
- Корневая команда `pnpm check` запускает проверку типов обоих приложений, ESLint, dependency-cruiser и проверку актуальности OpenAPI и клиентских типов. CI выполняет эту же команду на pull request. Проверки работают без запущенного Compose.
- Основное локальное окружение состоит из сервисов web, api, db и rabbitmq в Docker Compose. Данные PostgreSQL и RabbitMQ сохраняются между обычными перезапусками в отдельных томах.
- Для обычного запуска полного стека используется `docker compose up --wait --wait-timeout <секунды>`. Проверки готовности в Compose заданы для всех четырёх сервисов. Проверка web обращается к его странице. Проверка API обращается к `/health/ready`.
- `pnpm smoke` запускает полный стек с ожиданием готовности и конечным таймаутом. Затем он вызывает общую команду готовности, которая проверяет страницу web и `/api/health/ready` по адресу web. Эта общая команда также запускается отдельно для уже работающего стека, в том числе при Compose Watch.
- Для запуска приложений на компьютере Compose поднимает только PostgreSQL и RabbitMQ с ожиданием готовности. После этого корневой `pnpm dev` запускает web и API на компьютере. Этот режим использует те же контейнеры и тома инфраструктуры. С первой предметной миграцией инструкция для этого режима включает запуск `migrate` через Compose до старта API.
- Compose Watch синхронизирует исходники. Vite обновляет frontend; NestJS перезапускает backend. Изменение зависимостей пересобирает соответствующий образ.
- Установленные зависимости остаются внутри контейнеров. Локальные секреты, служебные данные Git и результаты сборки исключаются из синхронизации.
- Db проверяется через pg_isready, rabbitmq — собственной проверкой готовности. Compose запускает api после готовности db и rabbitmq. Web запускается независимо от api.
- Api предоставляет /health/live для проверки ответа процесса. /health/ready выполняет SELECT 1 через соединение api с PostgreSQL и проверяет возможность открыть AMQP-канал с настроенными учётными данными. Ответ показывает состояние каждой зависимости.
- Если база или брокер недоступны либо проверка превышает таймаут, /health/ready возвращает HTTP 503. Таймаут БД охватывает получение соединения и выполнение SELECT 1. Таймаут RabbitMQ охватывает соединение и открытие канала. Проверки работают и после запуска.
- Готовность web проверяется HTTP-запросом к странице. Общая команда дополнительно запрашивает /api/health/ready по адресу web через прокси Vite. Отрисовка React проверяется отдельно в браузере.
- Техническая страница `/system` запрашивает существующий `/api/health/ready` через прокси Vite. Она показывает загрузку и отдельные состояния PostgreSQL и RabbitMQ при HTTP 200 и 503. Если API недоступен и ответ о готовности получить не удалось, страница сообщает об ошибке связи. Проверка страницы дополняет общую команду готовности.
- GitHub и Codex не входят в проверку готовности каркаса. Для запуска не нужны их учётные данные.
- По умолчанию web доступен на localhost:5173. Запросы браузера к /api/ идут через Vite с удалением префикса /api. В полном стеке Vite обращается к api:3000, а API — к db:5432 и rabbitmq:5672.
- По умолчанию с компьютера доступны API на 127.0.0.1:3000, PostgreSQL на 127.0.0.1:5432 и RabbitMQ на 127.0.0.1:5672. В режиме `pnpm dev` Vite использует локальный адрес API, а API подключается к опубликованным портам PostgreSQL и RabbitMQ. Опубликованные порты и слушатели приложений в режиме `pnpm dev` привязаны к 127.0.0.1. Внешние номера меняются локальными настройками.
- Реальные локальные значения хранятся вне Git. В репозитории хранится безопасный пример параметров. Секреты исключены из контекста сборки и синхронизации Watch.
- Каждый сервис получает только нужные ему параметры. API получает параметры PostgreSQL и RabbitMQ. Frontend получает только публичные значения. Параметры Vite с префиксом VITE_ считаются публичными.
- При отсутствии обязательного параметра запуск завершается с понятным названием параметра. Сообщения не раскрывают значения секретов.
- Корневой README.md описывает подготовку параметров, обычный запуск, Compose Watch и локальный запуск приложений через `pnpm dev`. В нём указаны адрес `/system`, команды генерации HTTP-контракта, `pnpm check`, `pnpm smoke` и проверка уже запущенного стека. README также описывает таймауты и остановку с сохранением данных.
- Вместе с приложениями создаются короткие `apps/api/AGENTS.md` и `apps/web/AGENTS.md`. Корневой `AGENTS.md` направляет агента к нужному файлу перед изменениями в соответствующем приложении.
- `apps/api/AGENTS.md` объясняет размещение обработчиков и указывает, когда читать ADR об Edge, границах модулей, событиях и миграциях. `apps/web/AGENTS.md` объясняет размещение маршрутов и страниц, указывает на код `/system` как пример типизированного запроса и описывает, когда проверять или перегенерировать клиентские типы.
- Локальные инструкции содержат указания для изменения кода и ссылки на действующие примеры. Команды запуска и проверок описываются в корневом README. Причины архитектурных решений остаются в ADR.

## Testing Decisions

Владелец подтвердил два уровня проверок: работающее окружение и статические архитектурные ограничения.

- Основной уровень — запущенное Compose-окружение. Проверяется наблюдаемое поведение web, api, PostgreSQL и RabbitMQ через HTTP и браузер. Используются реальные соединения API с базой и брокером.
- В репозитории пока нет приложений и существующих тестов. Готовых примеров проверок нет. Внутренние методы пустых модулей отдельно не тестируются.
- Главная положительная проверка: запустить окружение из безопасного примера настроек с локальными значениями; открыть React в браузере; обратиться с адреса web к /api/health/ready; получить успешный ответ после реального SELECT 1 и проверки AMQP-канала.
- В браузере на `/system` проверяются загрузка, отдельные статусы зависимостей при HTTP 200 и 503 и ошибка связи при недоступном API. При HTTP 503 экран показывает, какая зависимость не готова.
- Общая команда готовности завершается успешно, если страница web отвечает и запрос к /api/health/ready по адресу web возвращает HTTP 200. Отдельно проверяется, что команда возвращает ошибку при неисправном прокси, даже когда API и БД доступны напрямую. При недоступности web, API, БД или RabbitMQ команда также возвращает ошибку.
- `pnpm smoke` стартует из остановленного окружения и проходит после успешной проверки через web. При неисправном прокси или истечении срока ожидания команда возвращает ненулевой код.
- В режиме `pnpm dev` в Compose запущены только PostgreSQL и RabbitMQ. Web и API запускаются на компьютере. На странице `/system` через прокси Vite видны результаты проверок обеих зависимостей.
- После остановки db api перестаёт сообщать готовность. Проверка /health/live продолжает отвечать, пока сам процесс api работает. После восстановления соединения проверка готовности снова проходит.
- При задержке БД или RabbitMQ дольше таймаута соответствующей проверки /health/ready возвращает HTTP 503 и указывает неготовую зависимость. Проверка /health/live продолжает отвечать.
- После остановки RabbitMQ /health/ready возвращает HTTP 503 и указывает RabbitMQ как неготовый. /health/live продолжает отвечать. После восстановления брокера API снова подтверждает готовность без ручного перезапуска. Отдельно проверяются неверные параметры подключения API к работающему брокеру.
- Неверные учётные данные api приводят к неуспешной готовности даже при успешном pg_isready. Для проверки меняется соединение api с уже настроенной базой, а не ожидается автоматическая смена пароля существующего тома.
- При недоступном api web продолжает обслуживать страницу. Успех HTTP-проверки web не считается доказательством успешной отрисовки React.
- Сохранение данных проверяется техническим SQL-примером: записать значение, выполнить обычную остановку и повторный запуск, прочитать значение. Временные данные проверки очищаются; предметные таблицы не добавляются.
- Подхват изменений проверяется через Watch: изменение frontend видно в браузере; изменение backend вызывает его перезапуск; изменение зависимостей пересобирает нужный образ. Проверки могут быть описаны как воспроизводимая ручная приёмка.
- Отдельный статический уровень проверяет архитектурные ограничения. Допустимые импорты проходят; запрещённая связь модулей, импорт внутреннего файла и цикл завершаются ошибкой. Проверяются также импорты типов и разрешение через используемые псевдонимы TypeScript.
- Приёмка проверяет, что разрешённая зависимость через `public.ts` проходит. Импорт внутреннего файла через `import type` и псевдоним TypeScript отклоняется. Импорт `*.module.ts` проходит в коде сборки NestJS и отклоняется в обычном межмодульном коде.
- При импорте внутреннего файла модуля, к которому разрешено обращаться, сообщение показывает импорт и нарушенное правило. Оно подсказывает заменить импорт обращением к `public.ts`.
- Для FSD проверяются направления между слоями, закрытые файлы чужого слайса и исключения App/Shared. Импорт исходников backend из frontend отклоняется.
- Отрицательные примеры импортов размещаются во временных проверочных файлах либо изолированных примерах. Они не остаются пользовательскими модулями и не требуют вымышленных операций в рабочем коде.
- `pnpm check` проходит на корректном каркасе без запущенного Compose. В GitHub подтверждается запуск этой команды для pull request и неуспешный результат при архитектурном нарушении. Проверка локальной команды не заменяет проверку фактического запуска workflow.
- Проверка контракта проходит при актуальных OpenAPI и клиентских типах. Приёмка CI подтверждает, что проверка падает и при устаревшем OpenAPI, и при устаревших клиентских типах.
- Для параметров проверяется отказ при отсутствии обязательного значения. Проверяется исключение реального локального файла из Git, контекста сборки и Watch. Секреты PostgreSQL и RabbitMQ не передаются web и не входят в браузерную сборку.
- Хорошая проверка наблюдает результат: HTTP-ответ, код завершения команды, сохранённое значение либо изменение страницы. Она не закрепляет внутренний порядок вызовов, имена вспомогательных методов и устройство пустых классов.
- Приёмка документации проверяет, что ссылки из корневого и локальных `AGENTS.md` ведут к существующим файлам, а команды из README соответствуют каркасу.
- Статический анализ импортов не доказывает авторизацию, корректность транзакций или отсутствие чужого произвольного SQL. Эти свойства проверяются при реализации соответствующих функций.
- В отчёте отделяются выполненные автоматические проверки, ручная приёмка, локальные результаты и результаты GitHub. Если Docker недоступен, запуск окружения не считается подтверждённым.

## Out of Scope

- Приглашения, вход и роли, управление сотрудниками, проектами и назначениями.
- Реализация Edge для защищённых запросов, включая проверку сессии и подключения Codex.
- Пользовательские страницы, формы и навигация между пользовательскими разделами. Tailwind CSS и компоненты SmoothUI подключаются с первым пользовательским интерфейсом.
- Подключение Codex, выбор протокола, персональные токены и отзыв подключения.
- Настройка интеграции GitHub, выдача и отзыв реальных прав, сверка и повторы после сбоев.
- Начальная настройка первого администратора.
- Предметные таблицы, предметные миграции, демонстрационные учётные записи и начальные пользовательские данные.
- Создание схем модулей, настройка двух ролей PostgreSQL и сервис `migrate`. Они появляются с первыми предметными таблицами и миграциями.
- Механизм транзакций между модулями, хранение незавершённых сверок и обработка устаревших результатов.
- Проверка прав перед отправкой ответа Codex и отзыв доступа во время отправки частями.
- Предметные очереди, публикация и обработка событий, хранение событий перед отправкой (outbox) и защита от повторной обработки. Они реализуются с первым предметным событием.
- Микросервисы и другие сервисы без согласованной необходимости.
- Рабочий хостинг, производственная конфигурация, развёртывание и дополнительные внешние интеграции.
- Обновление системных инструментов компьютера без отдельной необходимости и согласования.
