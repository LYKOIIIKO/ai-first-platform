# Технический каркас платформы и локальное окружение

Статус: спецификация согласована. Владелец подтвердил уровни проверок по процессу to-spec.

Опубликовано: [GitHub issue #1](https://github.com/LYKOIIIKO/ai-first-platform/issues/1), метка ready-for-agent. Опубликованный текст проверен; эта ссылка добавлена в локальную копию после публикации.

## Problem Statement

Владелец начинает учебный проект и хочет изучить новые технологии на реальной архитектуре платформы. В репозитории уже согласованы требования, термины, предметная модель и технические решения. Исполняемых приложений и локального окружения пока нет.

Без общего каркаса нельзя проверить соединение интерфейса, backend и базы. Нельзя автоматически обнаружить нарушения границ модулей. Разные настройки компьютеров также могут мешать повторяемому запуску.

Нужна минимальная техническая основа для последующей реализации первой версии. На этом этапе пользовательские функции не реализуются.

## Solution

Подготовить единый репозиторий с отдельными frontend и backend, PostgreSQL и общими командами. Запускать три сервиса через Docker Compose. Обеспечить обновление исходников, проверки готовности и безопасные локальные настройки.

Зафиксировать границы пяти предметных модулей и структуру frontend по FSD. Настроить автоматические проверки импортов локально и для pull request. Создать только необходимые точки входа и технические обработчики готовности.

## Implementation Decisions

- Цель задачи — реализовать согласованный технический каркас. Учебная ценность важнее минимального времени разработки.
- Backend: Node.js, TypeScript и NestJS. Frontend: React, TypeScript и Vite. База: PostgreSQL. Доступ к базе: Drizzle ORM, SQL-миграции через Drizzle Kit.
- Ветки среды: Node.js 24 LTS, PostgreSQL 18 и pnpm 12. Точные совместимые версии закрепляются при реализации. Не подменять согласованные ветки молча, если обнаружится проблема доступности или совместимости.
- Репозиторий объединяет два приложения в pnpm workspace. Каждое приложение имеет собственные зависимости и команды. Из корня доступны общие команды установки, запуска и проверок. Используется общий lock-файл.
- Общие пакеты появляются при наличии реального общего кода. Пустые пакеты для предполагаемых будущих потребностей не создавать.
- Backend — модульный монолит. Пять предметных модулей: «Сотрудники», «Проекты», «Доступ», «Подключения агентов» и «Интеграции».
- «Сотрудники» отвечают за приглашения, учётные записи, вход через GitHub, состояние и роль. «Проекты» отвечают за состав проектов, репозитории и инструкции.
- «Доступ» отвечает за назначения, требуемые права и сверку прав. «Подключения агентов» отвечают за действительность подключений Codex. «Интеграции» выполняют операции с внешними сервисами от имени компании.
- Эта ответственность задаёт границы будущей реализации. Данная задача создаёт точки входа модулей, но не реализует перечисленные пользовательские операции.
- У предметного модуля две открытые точки входа: контракт и сборка NestJS. Внутренние файлы, включая описания таблиц, закрыты для других модулей.
- Каждая будущая таблица принадлежит одному модулю. Другие модули обращаются к владельцу через его интерфейс. Прямое чтение или изменение чужих таблиц запрещено.
- Типы строк и вставок выводятся из описаний Drizzle. Повторные ручные описания тех же полей не требуются. Предметные таблицы в этой задаче не создаются.
- Основной обмен между модулями — прямые вызовы внутри процесса. Асинхронный вызов сам по себе не обеспечивает сохранение незавершённой работы.
- Сквозные действия координирует прикладной слой над предметными модулями. Он не дублирует предметные правила. В этой задаче будущие сценарии и их методы не создаются.
- Прикладные сценарии могут обращаться к любому необходимому предметному модулю. Предметные модули не вызывают прикладные сценарии.
- «Доступ» может зависеть от «Сотрудников», «Проектов» и «Интеграций». «Подключения агентов» могут зависеть от «Сотрудников».
- «Сотрудники», «Проекты» и «Интеграции» не зависят от других предметных модулей. Остальные предметные зависимости запрещены. Общая техническая инфраструктура не считается дополнительным предметным модулем.
- Ответственность за повторы и актуальность сверок остаётся у «Доступа». «Интеграции» выполняют одну попытку сверки. Технический каркас не переносит эту ответственность в прикладной слой.
- Отдельно размещаются запуск backend, сборка NestJS, прикладной слой, предметные модули, транспорт и техническая инфраструктура. Не создавать методы, классы и внутренние каталоги будущих операций.
- Frontend использует FSD. Предусмотрены слои app, pages, widgets, features, entities и shared. Они появляются по необходимости; для каркаса достаточно реально используемых частей.
- Слайсы используют нижележащие слои через открытые точки входа с именованными экспортами. Связи слайсов одного слоя по умолчанию запрещены. Внутренние файлы не импортируют собственную открытую точку входа.
- App и Shared состоят из сегментов без слайсов. Связи между сегментами внутри этих слоёв разрешены. Для Shared открытые точки входа определяются по сегменту или отдельной библиотеке либо компоненту.
- Специальные связи сущностей FSD через @x требуют отдельной реальной потребности. В каркасе такие исключения не вводятся.
- Frontend обращается к backend по HTTP. Импорты серверных исходников и описаний Drizzle из frontend запрещены.
- Dependency-cruiser проверяет матрицу зависимостей, открытые точки входа и циклы. Разрешение импортов учитывает настройки TypeScript. Импорты типов подчиняются тем же правилам.
- ESLint no-restricted-imports даёт раннюю обратную связь для простых запретов, включая доступ к чужим внутренним файлам. Полную матрицу не дублировать вручную в двух конфигурациях.
- Правила охватывают backend и согласованные границы FSD. Нарушение завершает проверку с ошибкой локально и при проверке pull request в GitHub.
- Основное локальное окружение состоит из сервисов web, api и db в Docker Compose. Данные PostgreSQL сохраняются между обычными перезапусками.
- Compose Watch синхронизирует исходники. Vite обновляет frontend; NestJS перезапускает backend. Изменение зависимостей пересобирает соответствующий образ.
- Установленные зависимости остаются внутри контейнеров. Локальные секреты, служебные данные Git и результаты сборки исключаются из синхронизации.
- Db проверяется через pg_isready. Api запускается после готовности db. Web запускается независимо от api.
- Api предоставляет /health/live для проверки ответа процесса и /health/ready для выполнения SELECT 1 через собственное настроенное соединение с базой. Проверка готовности работает и после запуска.
- Если соединение с базой недоступно, /health/ready возвращает неуспешный HTTP-статус. Pg_isready не заменяет проверку настоящего соединения api.
- Готовность web проверяется HTTP-запросом. Общая команда подтверждает доступность web и готовность api с базой. Отрисовка React проверяется отдельно в браузере.
- GitHub и Codex не входят в проверку готовности каркаса. Для запуска не нужны их учётные данные.
- По умолчанию web доступен на localhost:5173. Запросы браузера к /api/ идут через Vite в api:3000 с удалением префикса /api. Api подключается к db:5432.
- Для отладки api доступен с компьютера на localhost:3000, PostgreSQL — на localhost:5432. Публикуемые порты привязаны к 127.0.0.1. Внешние номера меняются локальными настройками; внутренние остаются фиксированными.
- Реальные локальные значения хранятся вне Git. В репозитории хранится безопасный пример параметров. Секреты исключены из контекста сборки и синхронизации Watch.
- Каждый сервис получает только нужные ему параметры. Frontend получает только публичные значения. Параметры Vite с префиксом VITE_ считаются публичными.
- При отсутствии обязательного параметра запуск завершается с понятным названием параметра. Сообщения не раскрывают значения секретов.
- Инструкция описывает подготовку параметров, запуск Watch, проверку готовности, общие команды и обычную остановку с сохранением данных.

## Testing Decisions

Владелец подтвердил два уровня проверок: работающее окружение и статические архитектурные ограничения.

- Основной уровень — запущенное Compose-окружение. Проверяется наблюдаемое поведение web, api и настоящей PostgreSQL через HTTP и браузер. Соединение с базой не подменяется имитацией.
- В репозитории пока нет приложений и существующих тестов. Готовых примеров проверок нет. Внутренние методы пустых модулей отдельно не тестируются.
- Главная положительная проверка: запустить окружение из безопасного примера настроек с локальными значениями; открыть React в браузере; обратиться с адреса web к /api/health/ready; получить успешный ответ после реального SELECT 1.
- Общая команда готовности завершается успешно только при доступном web и готовом api с базой. Если api или база недоступны, команда возвращает ошибку.
- После остановки db api перестаёт сообщать готовность. Проверка /health/live продолжает отвечать, пока сам процесс api работает. После восстановления соединения проверка готовности снова проходит.
- Неверные учётные данные api приводят к неуспешной готовности даже при успешном pg_isready. Для проверки меняется соединение api с уже настроенной базой, а не ожидается автоматическая смена пароля существующего тома.
- При недоступном api web продолжает обслуживать страницу. Успех HTTP-проверки web не считается доказательством успешной отрисовки React.
- Сохранение данных проверяется техническим SQL-примером: записать значение, выполнить обычную остановку и повторный запуск, прочитать значение. Временные данные проверки очищаются; предметные таблицы не добавляются.
- Подхват изменений проверяется через Watch: изменение frontend видно в браузере; изменение backend вызывает его перезапуск; изменение зависимостей пересобирает нужный образ. Проверки могут быть описаны как воспроизводимая ручная приёмка.
- Отдельный статический уровень проверяет архитектурные ограничения. Допустимые импорты проходят; запрещённая связь модулей, импорт внутреннего файла и цикл завершаются ошибкой. Проверяются также импорты типов и разрешение через используемые псевдонимы TypeScript.
- Для FSD проверяются направления между слоями, закрытые файлы чужого слайса и исключения App/Shared. Импорт исходников backend из frontend отклоняется.
- Отрицательные примеры импортов размещаются во временных проверочных файлах либо изолированных примерах. Они не остаются пользовательскими модулями и не требуют вымышленных операций в рабочем коде.
- В GitHub проверяется запуск архитектурных проверок для pull request и неуспешный результат при нарушении. Проверка локальной команды не заменяет проверку фактического запуска workflow.
- Для параметров проверяется отказ при отсутствии обязательного значения. Проверяется исключение реального локального файла из Git, контекста сборки и Watch. Секреты базы не передаются web и не входят в браузерную сборку.
- Хорошая проверка наблюдает результат: HTTP-ответ, код завершения команды, сохранённое значение либо изменение страницы. Она не закрепляет внутренний порядок вызовов, имена вспомогательных методов и устройство пустых классов.
- Статический анализ импортов не доказывает авторизацию, корректность транзакций или отсутствие чужого произвольного SQL. Эти свойства проверяются при реализации соответствующих функций.
- В отчёте отделяются выполненные автоматические проверки, ручная приёмка, локальные результаты и результаты GitHub. Если Docker недоступен, запуск окружения не считается подтверждённым.

## Out of Scope

- Приглашения, вход и роли, управление сотрудниками, проектами и назначениями.
- Пользовательские страницы, формы, навигация и выбор библиотек загрузки данных.
- Подключение Codex, выбор протокола, персональные токены и отзыв подключения.
- Настройка интеграции GitHub, выдача и отзыв реальных прав, сверка и повторы после сбоев.
- Начальная настройка первого администратора.
- Предметные таблицы, предметные миграции, демонстрационные учётные записи и начальные пользовательские данные.
- Механизм транзакций между модулями, хранение незавершённых сверок и обработка устаревших результатов.
- Проверка прав перед отправкой ответа Codex и отзыв доступа во время отправки частями.
- Очереди, микросервисы и другие сервисы без согласованной необходимости.
- Рабочий хостинг, производственная конфигурация, развёртывание и дополнительные внешние интеграции.
- Обновление системных инструментов компьютера без отдельной необходимости и согласования.
