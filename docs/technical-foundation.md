# Техническая основа первой версии

Документ объединяет решения от 11 и 20 ноября 2026 года. Проект учебный, поэтому изучение новых технологий важнее скорости реализации. Функциональные требования и термины определяются [требованиями заказчика](../customer-requirements.md), [границами первой версии](first-version.md), [словарём](../DOMAIN.md) и [предметной моделью](domain-model.md).

Статус: решения согласованы и записаны. Код приложений, конфигурации workspace, Docker и проверок пока не созданы. Документ не является отчётом о работающей реализации.

## Модули и взаимодействие

Backend — модульный монолит с пятью предметными модулями: «Сотрудники», «Проекты», «Доступ», «Подключения агентов» и «Интеграции». Их ответственность сохраняется из [предметной модели](domain-model.md#согласованная-ответственность-модулей). [ADR-0006](adr/0006-modular-monolith.md).

У каждой таблицы один модуль-владелец. Другие модули получают данные через его интерфейс. Прямые обращения к чужим таблицам запрещены. Решения в рамках запроса используют прямые вызовы интерфейсов внутри приложения. Сквозные действия координируют прикладные сценарии. RabbitMQ доставляет события для фоновых последствий. Первый сценарий с событием — отключение сотрудника. Событие сохраняется вместе с изменением учётной записи, а обработчики допускают повторную доставку. [Владение данными](adr/0007-module-data-ownership.md), [обмен](adr/0008-in-process-module-calls.md), [координация](adr/0009-application-scenarios.md).

У каждого предметного модуля своя схема в общей базе PostgreSQL. Схема появляется с первой таблицей модуля. Drizzle Kit ведёт одну общую историю миграций. С первой предметной миграцией отдельный сервис `migrate` меняет структуру базы до запуска API. API использует отдельную роль для чтения и записи данных. [Владение данными](adr/0007-module-data-ownership.md) · [Миграции](adr/0005-drizzle.md).

| Вызывающий код | Разрешённые предметные модули |
| --- | --- |
| Прикладной сценарий | Любой из пяти модулей, необходимый сценарию. |
| Доступ | Сотрудники, Проекты, Интеграции. |
| Подключения агентов | Сотрудники. |
| Сотрудники, Проекты, Интеграции | Другие предметные модули не вызываются. |

Предметные модули не вызывают прикладные сценарии. Связи, отсутствующие в таблице, запрещены. Устройство общей технической инфраструктуры определяется отдельно. [ADR-0010](adr/0010-allowed-module-dependencies.md).

Dependency-cruiser проверяет полную матрицу импортов, открытые точки входа и циклы. ESLint no-restricted-imports даёт ранние сообщения об отдельных запрещённых импортах. Сообщения показывают импорт и нарушенное правило. При наличии допустимой точки входа они подсказывают её. Импорты типов подчиняются тем же ограничениям. Проверки предусматриваются локально и при проверке pull request в GitHub. Настройка пока не выполнена. [ADR-0011](adr/0011-module-dependency-checks.md).

`pnpm check` объединяет проверку типов, ESLint, dependency-cruiser и проверку актуальности HTTP-контракта и клиентских типов. CI запускает эту же команду на pull request без Compose. Предметный код должен быть независим от NestJS, Drizzle, RabbitMQ и транспорта. Проверка этого правила появится с первым кодом предметных правил. [ADR-0011](adr/0011-module-dependency-checks.md).

## Размещение кода и точки входа

Для frontend выбран каталог apps/web, для backend — apps/api. У приложений будут собственные package.json и команды; общие команды будут запускаться из корня. Общие пакеты выделяются при появлении реального общего кода. [ADR-0012](adr/0012-monorepository.md).

Схема размещения backend:

```text
apps/api/src/
├── main.ts
├── app.module.ts
├── application/
├── modules/
│   ├── employees/
│   ├── projects/
│   ├── access/
│   ├── agent-connections/
│   └── integrations/
├── transport/
└── infrastructure/
```

У предметного модуля две открытые точки входа: public.ts для типов и описаний возможностей, а также файл *.module.ts для сборки NestJS. Остальные детали, включая описания таблиц, остаются внутри владельца. Точки входа подчиняются матрице зависимостей. [ADR-0013](adr/0013-backend-layout.md).

Входной слой (Edge) находится внутри transport. Он проверяет сессию сотрудника или подключение Codex и актуальное состояние учётной записи. Затем он передаёт прикладному сценарию подтверждённые идентификаторы. Правила доступа к проектам остаются в модуле «Доступ». Перед началом отправки ответа Codex сценарий повторно проверяет права на выдаваемые сведения. Каркас фиксирует ответственность Edge. Проверки появятся с первыми защищёнными запросами. [Входной слой](adr/0013-backend-layout.md) · [Прикладные сценарии](adr/0009-application-scenarios.md).

Frontend организуется по FSD со слоями app, pages, widgets, features, entities и shared. Слои и слайсы добавляются по необходимости. Слайсы используют нижележащие слои через открытые точки входа index.ts с именованными экспортами. Внутренние файлы слайса не импортируют собственную открытую точку входа. Исключения для App, Shared и специальных связей Entities описаны в [ADR-0014](adr/0014-frontend-fsd.md).

Начальные точки входа frontend — index.html и src/main.tsx; корневой компонент находится в app. Frontend взаимодействует с backend по HTTP и не импортирует исходники apps/api.

Схемы размещения обозначают согласованное устройство будущего кода. Пользовательские операции, классы, таблицы и каталоги будущих функций заранее не создаются.

## Локальное окружение

Для основного режима выбран Docker Compose с web, api, db и rabbitmq. PostgreSQL и RabbitMQ сохраняют данные в отдельных томах между обычными перезапусками. Compose Watch будет синхронизировать исходники; Vite — обновлять интерфейс, NestJS — перезапускать backend. Изменение зависимостей требует пересборки соответствующего образа. Node_modules должен оставаться внутри контейнеров. [Сервисы](adr/0016-local-compose.md), [Watch](adr/0021-compose-watch.md).

Обычный запуск полного стека через `docker compose up --wait` имеет конечный таймаут. `pnpm smoke` выполняет такой запуск и проверяет готовность через прокси web. Для отладки можно запустить в Compose только PostgreSQL и RabbitMQ, а web и API — на компьютере через `pnpm dev`. [Режимы запуска](adr/0016-local-compose.md) · [Проверки готовности](adr/0017-local-readiness.md).

| Соединение после запуска окружения | Предусмотренный адрес по умолчанию |
| --- | --- |
| Браузер → web | http://localhost:5173. |
| Браузер → backend | /api/ на адресе web. |
| Прокси Vite → api | http://api:3000; префикс /api удаляется. |
| Api → PostgreSQL | db:5432. |
| Api → RabbitMQ | rabbitmq:5672. |
| Компьютер → api для отладки | http://localhost:3000. |
| Компьютер → PostgreSQL | localhost:5432. |
| Компьютер → RabbitMQ | 127.0.0.1:5672. |

Публикуемые порты привязываются к 127.0.0.1. Внешние номера можно менять в локальных настройках. [ADR-0019](adr/0019-local-networking.md).

Для готовности предусмотрены раздельные проверки:

- Db: pg_isready должен подтверждать приём соединений.
- Api: /health/live должен подтверждать ответ процесса.
- RabbitMQ: собственная проверка готовности брокера.
- Api: /health/ready выполняет SELECT 1 и проверяет доступность AMQP-канала с настроенными учётными данными. Ответ показывает состояние каждой зависимости.
- Web: HTTP-запрос должен подтверждать обслуживание страницы; отрисовка React и запрос к backend подлежат дополнительной проверке браузером.
- Страница `/system` показывает загрузку, результаты PostgreSQL и RabbitMQ при HTTP 200 и 503, а также ошибку связи при недоступном API. Она использует существующий `/api/health/ready` через прокси. [ADR-0022](adr/0022-http-contract.md).

Api запускается после готовности db и rabbitmq, а web — независимо от api. Общая команда проверяет страницу web и готовность API через /api/health/ready по адресу web. При недоступности БД или RabbitMQ либо превышении таймаута API возвращает HTTP 503. Команды запуска и проверок и значения таймаутов будут в корневом README.md. GitHub не включается в общую готовность: при его сбое платформа должна показывать ошибки и продолжать повторные сверки. [ADR-0017](adr/0017-local-readiness.md).

В Git будет храниться .env.example с безопасными примерами. Локальный .env будет содержать реальные значения и должен исключаться из Git и контекста сборки. Каждый сервис должен получать только необходимые параметры; web — только публичные значения. Каркас использует параметры PostgreSQL и RabbitMQ. [ADR-0018](adr/0018-local-settings-and-secrets.md).

Вместе с приложениями появятся `apps/api/AGENTS.md` и `apps/web/AGENTS.md`. Корневой `AGENTS.md` направляет агента к нужному файлу. API-инструкция указывает на решения об Edge, модулях, событиях и миграциях. Web-инструкция описывает размещение маршрутов и работу с клиентскими типами. Код `/system` служит примером запроса к API. Команды запуска и проверок остаются в корневом README.

## Что осталось до реализации функций

Эти вопросы требуют отдельного проектирования и не считаются решёнными выбором стека:

- Способы подключения GitHub и Codex, авторизация и начальная настройка первого администратора.
- Транзакции при согласованном изменении нескольких модулей.
- Проверка актуальности прав непосредственно перед отправкой ответа Codex и поведение при отправке частями.
- Доставка и обработка первого предметного события, включая outbox и защиту от повторной обработки.
- Хранение и выполнение незавершённых сверок GitHub, интервалы повторов и подтверждение результата после потери ответа.
- Конкретные таблицы, обработчики пользовательских запросов, маршруты frontend и запросы отдельных экранов.
- Внешние ключи между схемами модулей. Решение принимается при проектировании первого назначения проекта.
- Детали общей технической инфраструктуры.
- Размещение рабочей версии платформы и план реализации функций.

Требования к сверке уже согласованы в [интерфейсе сверки](design/github-access-reconciliation.md). Они сохраняются независимо от выбранной реализации.

Код приложений, Compose-файл, файлы образов, health-обработчики, настройки проверок импортов и GitHub-проверки не подготовлены. Приложения, готовность соединений и подхват изменений не проверялись. Эти ограничения относятся к состоянию на дату обсуждения, а не к результату будущей реализации.
