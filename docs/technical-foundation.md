Функциональные требования и термины определяются [требованиями заказчика](../customer-requirements.md), [границами первой версии](first-version.md), [словарём](../DOMAIN.md) и [предметной моделью](domain-model.md).

Статус: решения согласованы и записаны. Код приложений, конфигурации workspace, Docker и проверок пока не созданы. Документ не является отчётом о работающей реализации.

## Модули и взаимодействие

Backend — модульный монолит с пятью предметными модулями: «Сотрудники», «Проекты», «Доступ», «Подключения агентов» и «Интеграции». Их ответственность сохраняется из [предметной модели](domain-model.md#согласованная-ответственность-модулей). [ADR-0006](adr/0006-modular-monolith.md).

У каждой таблицы один модуль-владелец. Другие модули получают данные через его интерфейс. Прямые обращения к чужим таблицам запрещены. Основной способ обмена — прямые вызовы интерфейсов внутри приложения. Сквозные действия координируют отдельные прикладные сценарии. [Владение данными](adr/0007-module-data-ownership.md), [обмен](adr/0008-in-process-module-calls.md), [координация](adr/0009-application-scenarios.md).

| Вызывающий код | Разрешённые предметные модули |
| --- | --- |
| Прикладной сценарий | Любой из пяти модулей, необходимый сценарию. |
| Доступ | Сотрудники, Проекты, Интеграции. |
| Подключения агентов | Сотрудники. |
| Сотрудники, Проекты, Интеграции | Другие предметные модули не вызываются. |

Предметные модули не вызывают прикладные сценарии. Связи, отсутствующие в таблице, запрещены. Устройство общей технической инфраструктуры определяется отдельно. [ADR-0010](adr/0010-allowed-module-dependencies.md).

Dependency-cruiser проверяет полную матрицу импортов, открытые точки входа и циклы. ESLint no-restricted-imports даёт ранние сообщения об отдельных запрещённых импортах. Импорты типов подчиняются тем же ограничениям. Проверки предусматриваются локально и при проверке pull request в GitHub; настройка пока не выполнена. [ADR-0011](adr/0011-module-dependency-checks.md).

## Размещение кода и точки входа

Для frontend выбран каталог apps/web, для backend — apps/api. У приложений будут собственные package.json и команды; общие команды будут запускаться из корня. Общие пакеты выделяются при появлении реального общего кода. [ADR-0012](adr/0012-monorepository.md).

Схема размещения backend:

```text
apps/api/src/
├── main.ts
├── app.module.ts
├── application/
├── modules/
│   ├── employees/
│   ├── projects/
│   ├── access/
│   ├── agent-connections/
│   └── integrations/
├── transport/
└── infrastructure/
```

У предметного модуля две открытые точки входа: public.ts для типов и описаний возможностей, а также файл *.module.ts для сборки NestJS. Остальные детали, включая описания таблиц, остаются внутри владельца. Точки входа подчиняются матрице зависимостей. [ADR-0013](adr/0013-backend-layout.md).

Frontend организуется по FSD со слоями app, pages, widgets, features, entities и shared. Слои и слайсы добавляются по необходимости. Слайсы используют нижележащие слои через открытые точки входа index.ts с именованными экспортами. Внутренние файлы слайса не импортируют собственную открытую точку входа. Исключения для App, Shared и специальных связей Entities описаны в [ADR-0014](adr/0014-frontend-fsd.md).

Начальные точки входа frontend — index.html и src/main.tsx; корневой компонент находится в app. Frontend взаимодействует с backend по HTTP и не импортирует исходники apps/api.

Схемы размещения обозначают согласованное устройство будущего кода. Пользовательские операции, классы, таблицы и каталоги будущих функций заранее не создаются.

## Локальное окружение

Для основного режима выбран Docker Compose с web, api и db. PostgreSQL должен сохранять данные между перезапусками. Compose Watch будет синхронизировать исходники; Vite — обновлять интерфейс, NestJS — перезапускать backend. Изменение зависимостей требует пересборки соответствующего образа. Node_modules должен оставаться внутри контейнеров. [Сервисы](adr/0016-local-compose.md), [Watch](adr/0021-compose-watch.md).

| Соединение после запуска окружения | Предусмотренный адрес по умолчанию |
| --- | --- |
| Браузер → web | http://localhost:5173. |
| Браузер → backend | /api/ на адресе web. |
| Прокси Vite → api | http://api:3000; префикс /api удаляется. |
| Api → PostgreSQL | db:5432. |
| Компьютер → api для отладки | http://localhost:3000. |
| Компьютер → PostgreSQL | localhost:5432. |

Публикуемые порты привязываются к 127.0.0.1. Внешние номера можно менять в локальных настройках. [ADR-0019](adr/0019-local-networking.md).

Для готовности предусмотрены раздельные проверки:

- Db: pg_isready должен подтверждать приём соединений.
- Api: /health/live должен подтверждать ответ процесса.
- Api: /health/ready должен выполнять SELECT 1 через настроенное соединение с базой, в том числе после запуска.
- Web: HTTP-запрос должен подтверждать обслуживание страницы; отрисовка React и запрос к backend подлежат дополнительной проверке браузером.

Api должен запускаться после готовности db, а web — независимо от api. Предусматривается общая команда проверки. GitHub не включается в общую готовность: при его сбое платформа должна показывать ошибки и продолжать повторные сверки. [ADR-0017](adr/0017-local-readiness.md).

В Git будет храниться .env.example с безопасными примерами. Локальный .env будет содержать реальные значения и должен исключаться из Git и контекста сборки. Каждый сервис должен получать только необходимые параметры; web — только публичные значения. Для каркаса достаточно параметров PostgreSQL. [ADR-0018](adr/0018-local-settings-and-secrets.md).

## Что осталось до реализации функций

Эти вопросы требуют отдельного проектирования и не считаются решёнными выбором стека:

- Способы подключения GitHub и Codex, авторизация и начальная настройка первого администратора.
- Транзакции при согласованном изменении нескольких модулей.
- Проверка актуальности прав непосредственно перед отправкой ответа Codex и поведение при отправке частями.
- Хранение и выполнение незавершённых сверок GitHub, интервалы повторов и подтверждение результата после потери ответа.
- Конкретная схема таблиц, обработчики пользовательских запросов, маршрутизация frontend и загрузка данных.
- Выбор HTTP-адаптера NestJS и детали общей технической инфраструктуры.
- Размещение рабочей версии платформы и план реализации функций.

Требования к сверке уже согласованы в [интерфейсе сверки](design/github-access-reconciliation.md). Они сохраняются независимо от выбранной реализации.
