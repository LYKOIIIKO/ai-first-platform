# Сверка прав на репозитории GitHub

Интерфейс согласован для первой версии. «Доступ» определяет, какие права положены сотруднику по текущим назначениям. «Интеграции» сверяют требуемое право с GitHub и возвращают результат. Сверка выполняется отдельно для каждого репозитория сотрудника. При сбое с одним репозиторием успешно выданные права на остальные сохраняются. [Предметная модель](../domain-model.md#согласованная-ответственность-модулей), [частичная выдача прав](../first-version.md#частичная-выдача-прав).

## Интерфейс модулей

| Вариант | Где остаётся сложность |
| --- | --- |
| Отдельные операции чтения, выдачи и отзыва. | Каждый вызывающий сценарий должен учитывать приглашения, неопределённый результат и повторную проверку. |
| «Интеграции» принимают полный список требуемых прав сотрудника с номером версии. | Вызывающему модулю достаточно передать один список. «Доступу» нужно надёжно доставлять версии, а «Интеграциям» хранить последнюю принятую версию и состояние по каждому репозиторию. |
| «Доступ» ведёт сверку, «Интеграции» выполняют одну проверяемую попытку. | «Доступ» обрабатывает версии и повторы рядом с назначениями. «Интеграции» в одном месте обрабатывают детали GitHub и подтверждают результат. |

Для первой версии выбрали третий вариант. Сценарии назначения, снятия назначения и отключения используют один порядок сверки. Интерфейс «Интеграций» принимает нужное состояние одной пары и скрывает последовательность операций GitHub. Изменения назначений и обработка устаревших результатов остаются рядом в модуле «Доступ».

```text
Интеграции.сверитьПрава(аккаунт GitHub, репозиторий, требуемый уровень)
  Требуемый уровень: права разработчика | доступ закрыт
  Результат: подтверждено | ожидает принятия приглашения | не подтверждено (причина)
```

«Интеграции» проверяют фактическое право и действующие приглашения. При необходимости модуль выдаёт или отзывает право, отменяет ненужное приглашение и проверяет результат. Статус «подтверждено» означает, что установлен требуемый уровень. Для закрытого доступа модуль также проверяет, что сотрудник не сможет получить доступ по оставшемуся приглашению платформы.

Если GitHub создал приглашение, платформа ждёт принятия и проверяет фактические права. Если ответ потерялся, платформа показывает, что результат неизвестен. Перед следующей попыткой «Интеграции» выясняют, что уже изменилось в GitHub. Платформа учитывает ограничения на повторы, возвращаемые GitHub. Ошибка чтения, включая `404` при недоступном интеграции репозитории, сама по себе не подтверждает отсутствие прав. [Выдача прав](https://docs.github.com/en/rest/collaborators/collaborators#add-a-repository-collaborator), [проверка прав](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user), [отмена приглашения](https://docs.github.com/en/rest/collaborators/invitations#delete-a-repository-invitation), [ошибки GitHub](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api).

## Порядок сверки

1. Когда меняется назначение, состав проекта или состояние учётной записи, «Доступ» сохраняет необходимость сверки затронутых пар вместе с изменением. Запись о незавершённой сверке сохраняется после перезапуска. При отключении в сверку попадают и пары, для которых выдача ещё выполняется или её результат неизвестен.
2. Перед каждой попыткой «Доступ» заново вычисляет нужный уровень по действующим назначениям и состоянию учётной записи. Платформа ведёт один цикл сверки на пару. Для разных репозиториев сверки могут идти независимо. Пока цикл работает, администратор может менять назначения.
3. «Доступ» принимает результат только для актуальной версии требуемого права. Если требование изменилось, результат старой операции служит поводом сверить пару снова с новым требованием. Актуальность проверяется при сохранении результата, чтобы параллельное изменение не затерялось.
4. При потере ответа платформа сохраняет неопределённость и продолжает сверку. Если отправленная ранее выдача ещё может сработать, одно наблюдение «права сейчас нет» недостаточно, чтобы завершить отзыв. То же верно для запоздавшего отзыва после повторного назначения. Пока интеграция не может подтвердить итог, платформа показывает причину и сохраняет работу на повторную проверку.

Отключение сотрудника и запрет на выдачу данных через платформу действуют сразу. Codex получает инструкции только после подтверждения прав на все репозитории по текущему назначению. Полное отключение подтверждается после завершения внешнего отзыва. [Граница отзыва](../first-version.md#граница-отзыва-доступа), [повтор операций](../first-version.md#повтор-операций-с-правами-github).

## Сценарии для проверки интерфейса

| Ситуация | Наблюдаемый результат |
| --- | --- |
| Платформа начала выдачу. Пока GitHub обрабатывал запрос, администратор снял единственное назначение. | Платформа сразу закрывает доступ к контексту проекта. После ответа она сверяет уже закрытый доступ, отзывает фактически выданное право или отменяет оставшееся приглашение. Устаревший ответ не помечает назначение готовым. |
| Платформа начала отзыв. Пока GitHub обрабатывал запрос, сотрудник получил другое назначение с тем же репозиторием. | Платформа сверяет доступ по новому назначению и восстанавливает его, если GitHub успел отозвать право. Она подтверждает готовность по фактическому результату новой сверки. |
| Один из двух проектов с общим репозиторием сняли. | Другое назначение по-прежнему даёт нужное право. Сверка сохраняет доступ в GitHub. |
| GitHub мог применить выдачу, но ответ потерялся. | Платформа не сообщает о готовности. Следующая попытка начинается с проверки GitHub. Если к тому времени сотрудника отключили, цель сверки меняется на закрытый доступ. |
| GitHub создал приглашение, которое сотрудник ещё не принял. | Codex пока не получает инструкции этого проекта. Если назначение снято и других оснований для выдачи нет, платформа отменяет приглашение и проверяет, что сотрудник не успел получить право. |
| Платформа остановилась между отправкой запроса и сохранением результата. | После перезапуска платформа возвращается к незавершённой сверке и заново проверяет GitHub. |

В реализации эти сценарии можно проверить через интерфейс сверки с тестовой заменой GitHub. Реальная проверка в пилоте нужна для приглашений, выдачи, отзыва и наблюдения за правами в выбранной организации. Проектирование конкретных API, подтверждения результата после неопределённого запроса, хранения незавершённых сверок и интервала повторов остаётся отдельным шагом.
