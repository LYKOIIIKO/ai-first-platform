# Предметная модель первой версии

Модель опирается на [согласованные границы первой версии](first-version.md) и [словарь проекта](../DOMAIN.md).

## Правила доступа

- Администратор приглашает конкретный GitHub-аккаунт. У аккаунта может быть только одно действующее приглашение. Новая ссылка заменяет прежнюю. Приглашение можно принять один раз. Администратор может отозвать ещё не принятое приглашение.
- При первом принятии приглашения платформа создаёт учётную запись с ролью «Разработчик» и без назначений. После принятия администратор назначает проекты и при необходимости меняет роль. Права на репозитории получает GitHub-аккаунт, который принял приглашение.
- У активной учётной записи одна роль платформы: «Администратор» или «Разработчик».
- Назначение проекта связывает сотрудника с проектом. Проект хранит ссылки на существующие репозитории GitHub и общие инструкции в Markdown. Один репозиторий может входить в несколько проектов.
- Администратор может сохранить проект без репозиториев. Для назначения проекта в нём должен быть хотя бы один репозиторий. Чтобы исключить последний репозиторий, администратор сначала снимает все назначения проекта.
- Администратор управляет всеми проектами и назначениями. Для чтения и редактирования инструкций и работы с репозиториями ему требуется назначение на этот проект. Через платформу Codex только читает доступные сотруднику проекты, репозитории и инструкции.
- В платформе должен оставаться хотя бы один активный администратор. Платформа блокирует отключение или снятие полномочий последнего активного администратора, пока администратором не станет другой активный сотрудник.
- У учётной записи может быть только одно действующее подключение Codex. Когда сотрудник создаёт новое подключение, платформа отзывает прежнее.
- При каждом новом запросе Codex платформа проверяет действительность подключения, состояние учётной записи и текущие назначения, даже если токен ещё действует. Отключение сотрудника блокирует новые запросы его агента. Снятие назначения закрывает агенту сведения этого проекта.
- Если права изменились до начала отправки ответа Codex, платформа выдаёт только сведения, которые остаются доступны сотруднику. Проверка в начале запроса сама по себе не даёт права получить данные после отзыва.
- Состав назначенных проектов определяет, к каким репозиториям сотруднику положен доступ. Фактическую выдачу и отзыв прав платформа подтверждает через GitHub. Условия пилота исключают дополнительные права через команды, базовые разрешения организации и общие ключи. [Условия пилота](first-version.md#условия-пилота).

## Что происходит при изменении доступа

| Событие | Результат |
| --- | --- |
| Сотруднику назначили проект или в проект добавили репозиторий. | Платформа пересчитывает требуемые права и выдаёт их в GitHub. Если часть операций не удалась, успешно выданные права сохраняются. Платформа показывает причину, повторяет неуспешные операции и отмечает назначение статусом «Доступ настраивается». Codex получает инструкции после подтверждения прав на все репозитории проекта. |
| Сотруднику сняли назначение или из проекта исключили репозиторий. | Платформа учитывает остальные назначения. Если они всё ещё дают доступ к этому репозиторию, право GitHub сохраняется. Иначе платформа отзывает его. |
| Сотрудника отключили. | Платформа сразу блокирует новые запросы сотрудника и отзывает его подключение Codex. Если GitHub недоступен, платформа показывает ошибку и повторяет отзыв прав на репозитории. Полное отключение подтверждается после отзыва прав в GitHub. Скачанные копии остаются у сотрудника. |
| Платформа готовится повторить выдачу или отзыв в GitHub. | Платформа пересчитывает нужные права по текущим назначениям, составу проектов и состоянию учётной записи. Она пропускает устаревшую операцию. Например, после снятия последнего назначения с этим репозиторием платформа больше не повторяет неудавшуюся выдачу. |
| Сотрудник возвращается после полного отключения с тем же GitHub-аккаунтом. | После принятия нового приглашения платформа активирует прежнюю учётную запись с ролью «Разработчик» и без назначений. Администратор заново назначает проекты и при необходимости меняет роль. Сотрудник заново подключает Codex. |
| Сотрудник отзывает подключение Codex. | Платформа сразу блокирует новые запросы через это подключение. Сотрудник может создать новое подключение. Его собственный доступ к проектам и репозиториям определяется назначениями. |

## Согласованная ответственность модулей

- Модуль **«Сотрудники»** ведёт приглашения и учётные записи платформы. Он отвечает за вход через GitHub, связь с GitHub-аккаунтом, состояние учётной записи и роль платформы.
- Модуль **«Проекты»** ведёт состав проекта, ссылки на репозитории GitHub и инструкции. Он выдаёт содержимое после проверки прав модулем «Доступ».
- Модуль **«Доступ»** ведёт назначения и применяет единые правила к сотруднику и его Codex. По текущим назначениям и составу проектов он определяет, какие права на репозитории положены сотруднику. Перед выдачей инструкций агенту модуль учитывает, подтверждены ли права на все репозитории проекта.
- Модуль **«Подключения агентов»** ведёт персональные подключения Codex к учётным записям сотрудников и проверяет, действует ли подключение. Какие сведения получит Codex, определяет модуль «Доступ».
- Модуль **«Интеграции»** отвечает за связь платформы с внешними сервисами от имени компании. Он выдаёт и отзывает права на репозитории в GitHub и проверяет, какие права фактически действуют.

Причину выбора и пример с общим репозиторием фиксирует [ADR-0001](adr/0001-access-and-github-permissions.md).

«Доступ» ведёт сверку отдельно для каждой пары «сотрудник и репозиторий». «Интеграции» выполняют одну попытку сверки с GitHub и возвращают результат. [Согласованный интерфейс](design/github-access-reconciliation.md#интерфейс-модулей).

## Что нужно уточнить

- Отзыв доступа во время отправки ответа Codex. Если выбранный способ подключения отправляет ответ частями, нужно определить, что делать с оставшимися частями после отзыва.
- Способ подтверждения результата в GitHub после потери ответа, хранение незавершённых сверок и интервалы повторов.
- Способ подключения Codex. Персональный MCP для чтения контекста можно проверить на сценарии подключения и отзыва.

Первый сквозной сценарий для приёмки можно пройти с одним сотрудником, одним проектом и одним закрытым репозиторием. Приёмка первой версии также охватывает общий репозиторий, частичную выдачу и повтор отзыва после сбоя GitHub.
