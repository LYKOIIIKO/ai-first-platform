# Разбор задач и PR учебной AI-first платформы

Для нашего проекта из учебного примера полезнее всего разделение ответственности за внутренние разрешения, содержимое проектов и права GitHub. Учебный проект запланировал первую поставку с готовыми правами на код. У нас выдача и отзыв прав на реальные репозитории входят в критерии первой версии. [Требования заказчика](../../customer-requirements.md#с-чего-хотим-начать), [первая версия](../first-version.md#реальный-рабочий-цикл).

## Issue #2 и PR #7. Границы первой поставки

29 октября владелец согласовал сценарий подключения разработчика и его локального агента. Основная поставка включала приглашение и вход, проекты с репозиториями и инструкциями, участие сотрудников, выдачу контекста в пределах прав и прекращение доступа через платформу. Для работы с кодом использовали уже выданные права GitHub. Привязка GitHub-аккаунта и выдача и отзыв управляемых платформой прав составили дополнительный этап. Конкретного агента и способ его подключения оставили открытыми. [Решение в Issue #2](https://github.com/KirillSachkov/ai-first-platform/issues/2#issuecomment-6493396961).

В исторической карте главы GitHub-доступы и MCP уже фигурировали. Согласованный учебный материал относил управление правами GitHub к дополнительной практике, и владелец подтвердил это деление в интервью. Оно позволяет проверить первый сценарий на заранее доступном коде. Полный путь от проектирования задачи до merge остался целью развития. Интеграцию задач, мониторинг, общие скиллы и управление рабочими процессами на тот момент отложили. Исследования готовых платформ и трекеров помогли сверить границы. Выигрыш в скорости работы оставался гипотезой. [Описание оснований и критерии в PR #7](https://github.com/KirillSachkov/ai-first-platform/pull/7/changes#diff-1d5d28b59d1067878e2d8bf00bbc3a8b9b1ee969d63d7d657489e887c5aedbad).

PR #7 добавил словарь `DOMAIN.md` и описание первой версии `docs/first-version.md`, обновил `README.md`. Документ задал проверяемые признаки готовности для подключения и отдельную проверку выдачи и отзыва GitHub-прав для дополнительного этапа. В `main` вошёл коммит `b6e0dd4`. Изменения касались документации. [PR #7](https://github.com/KirillSachkov/ai-first-platform/pull/7), [diff](https://github.com/KirillSachkov/ai-first-platform/pull/7/changes).

## Issue #8 и PR #9. Предметная модель и владелец разрешений

После отдельного интервью владелец утвердил правила приглашения, участия в проектах, работы с общими репозиториями, выдачи инструкций, подключения агента и отключения сотрудника. Администратор управляет настройками всех проектов, а их рабочий контекст получает через участие. Последний активный администратор сохраняет полномочия, пока их не передали другому активному сотруднику. Общий репозиторий остаётся виден через другое участие, при этом каждый проект сохраняет собственную границу доступа к инструкциям. При возвращении сотруднику назначают проекты заново. [Решение в Issue #8](https://github.com/KirillSachkov/ai-first-platform/issues/8#issuecomment-6494444644), [модель в diff PR #9](https://github.com/KirillSachkov/ai-first-platform/pull/9/changes#diff-f0bd478c80a23952c9c1e48d1453ab201186c056a225847d5f98e6d8a796a7da).

| Модуль | Ответственность в учебной модели |
| --- | --- |
| Сотрудники | Приглашения, вход, учётные записи и их активность. |
| Проекты | Состав проектов, репозитории, источники инструкций и выдача содержимого после проверки. |
| Доступ | Участие в проектах, административные полномочия и проверка разрешений. |
| Подключения агентов | Владелец и действительность каждого подключения, его отдельный отзыв. |
| Интеграции | Внешние операции GitHub на дополнительном этапе. Основание для выдачи определяет «Доступ», состав репозиториев определяют «Проекты». |

В ADR сравнили два варианта. Первый распределял участие и административные полномочия между «Проектами» и «Сотрудниками» и совмещал проверку доступа с выдачей содержимого. Второй поручал назначения и правила отдельному модулю «Доступ». Владелец выбрал второй, чтобы человек и агент получали данные по единым правилам. Цена решения в том, что сценарии изменения прав и чтения обращаются к одному модулю. «Доступ» использует сведения об активности сотрудника и действительности подключения, которыми владеют другие модули. [ADR-0001 в diff PR #9](https://github.com/KirillSachkov/ai-first-platform/pull/9/changes#diff-a7ed1ac5589759eb40ca3902a44090c6d56dab126f541207a27776dfafbd7c27).

PR #9 добавил `docs/domain-model.md` и `docs/adr/0001-platform-access-ownership.md`, обновил `DOMAIN.md`, `AGENTS.md`, `docs/agents/domain.md` и `README.md`. При проверке соответствия задаче нашли, что модель не назначала владельца входа. Коммит `096caf4` закрепил вход за «Сотрудниками». В `main` вошёл коммит `ecd1c4a`. Стек, схема базы, техническое взаимодействие модулей и протокол подключения остались открыты. [PR #9](https://github.com/KirillSachkov/ai-first-platform/pull/9), [исправление по ревью](https://github.com/KirillSachkov/ai-first-platform/pull/9/commits/096caf4bacdd92e19ffba3fc2a37804d02e16c27).

## Issue #1. Что добавилось после двух PR

Issue #1 остался открытой картой решений. 5 ноября владелец выделил три блока подготовки спецификаций. Первый охватывает подключение сотрудника к проекту, второй охватывает наблюдение за сессиями и учёт использования, третий описывает корпоративный доступ к моделям через шлюз и правила бюджета. 6 ноября владелец подтвердил три спецификации внутри первого блока. [Решение о трёх блоках](https://github.com/KirillSachkov/ai-first-platform/issues/1#issuecomment-6667023667), [принятие спецификаций](https://github.com/KirillSachkov/ai-first-platform/issues/1#issuecomment-6683131529).

| Спецификация | Что согласовали |
| --- | --- |
| [#48](https://github.com/KirillSachkov/ai-first-platform/issues/48) | Вход через OIDC-провайдер в инфраструктуре компании, приглашения, участие в проектах, метаданные инструкций и персональное подключение агента через MCP, протокол доступа к инструментам и данным, с правами только на чтение. |
| [#49](https://github.com/KirillSachkov/ai-first-platform/issues/49) | Чтение задач по запросу. Платформа проверяет участие в проекте и существующее право сотрудника на репозиторий GitHub. |
| [#50](https://github.com/KirillSachkov/ai-first-platform/issues/50) | Общий набор правил и скиллов хранится в Git. Проект применяет фиксированную ревизию через PR с ревью и сохраняет свои дополнения. |

#49 и #50 используют контракты #48. У каждой своя приёмка, и #48 можно принять самостоятельно. Это позволяет проверить подключение человека и агента, пока работа с задачами и общим набором правил идёт отдельно. Комментарий фиксирует согласование требований и плана проверок. Выбор OIDC-продукта, совместимость клиента с MCP, авторизация GitHub и средство применения общего набора остаются инженерными вопросами. [Принятие и зависимости](https://github.com/KirillSachkov/ai-first-platform/issues/1#issuecomment-6683131529).

В ноябрьских уточнениях владелец отдельно описал отзыв. После подтверждённого отзыва платформа отклоняет новые запросы в соответствующей области независимо от срока действия токена. Отключение сотрудника затрагивает все его подключения. Отзыв одного подключения и исключение из проекта имеют собственные области. Запрос, который уже прошёл проверку, может завершиться. Скачанные данные остаются на устройстве. [Решение о приглашениях и отзыве](https://github.com/KirillSachkov/ai-first-platform/issues/1#issuecomment-6667262692).

## Что перенести в наш проект

1. **Дать внутренним разрешениям одного владельца.** «Доступ» определяет, какие проекты положены сотруднику и какой контекст доступен его Codex. «Сотрудники» ведёт учётную запись и вход. «Проекты» владеет составом и Markdown. Модуль подключений определяет владельца и проверяет, действует ли подключение Codex. GitHub-интеграция выполняет внешнюю выдачу и отзыв прав и проверяет результат. Это предлагаемые границы ответственности. Форму модулей и реализацию стоит определить отдельно. [ADR учебного проекта](https://github.com/KirillSachkov/ai-first-platform/pull/9/changes#diff-a7ed1ac5589759eb40ca3902a44090c6d56dab126f541207a27776dfafbd7c27), [обязательные границы нашего приложения](../first-version.md#обязательные-границы-приложения).
2. **Разбить реализацию на проверяемые сценарии.** Начать с приглашения и GitHub-входа. Затем пройти сквозной путь с одним сотрудником, одним проектом и реальным закрытым репозиторием: выдача прав, получение инструкций в Codex, локальная проверка окружения и отключение. К приёмке первой версии добавить общий репозиторий двух проектов, частичную выдачу и повтор отзыва после сбоя GitHub. Назначения определяют, кому доступ положен. Ответы GitHub подтверждают, какие права уже действуют. Платформа выдаёт Codex инструкции после подтверждения прав на все репозитории проекта. При отключении платформа прекращает выдавать новые данные сразу, а внешний отзыв подтверждает после GitHub. [Общие репозитории](../first-version.md#общие-репозитории), [частичная выдача](../first-version.md#частичная-выдача-прав), [ошибка отзыва](../first-version.md#ошибка-отзыва-доступа).
3. **Уточнить два правила перед реализацией.** Предлагаю защитить последнего активного администратора и проверять отзыв при каждом новом запросе Codex, включая запрос с ещё действующим токеном. Административные полномочия и чтение контекста по назначению у нас уже разделены. Восстановление через новое приглашение без возврата старых прав тоже согласовано. [Модель учебного проекта](https://github.com/KirillSachkov/ai-first-platform/pull/9/changes#diff-f0bd478c80a23952c9c1e48d1453ab201186c056a225847d5f98e6d8a796a7da), [решение об отзыве](https://github.com/KirillSachkov/ai-first-platform/issues/1#issuecomment-6667262692), [возврат сотрудника в нашем проекте](../first-version.md#повторное-подключение-сотрудника).
4. **Проверить персональный MCP на Codex.** Это кандидат для открытого вопроса о подключении. Проверка должна показать, что Codex читает только разрешённый контекст и теряет доступ после отзыва. В учебной модели MCP отдаёт метаданные, а полные инструкции агент читает из Git. У нас общие инструкции хранятся в платформе, поэтому состав ответа нужно спроектировать для нашего сценария. OIDC с отдельной привязкой GitHub, инструкции только в Git, интеграция задач, общий набор правил через PR, мониторинг и шлюз моделей относятся к учебному объёму. [Решение об инструкциях и MCP](https://github.com/KirillSachkov/ai-first-platform/issues/1#issuecomment-6667200596), [наш вход](../first-version.md#вход-сотрудника), [наши инструкции](../first-version.md#инструкции-проекта), [открытые вопросы](../first-version.md#вопросы-следующего-этапа).

В документах проекта уже есть [словарь](../../DOMAIN.md) и [границы первой версии](../first-version.md). Следующий документ по примеру PR #9 может описывать отношения, жизненные циклы и ответственность модулей. Когда владелец подтвердит выбор, отдельный ADR зафиксирует компромисс по владению разрешениями.
