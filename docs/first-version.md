# Первая версия

Источник обязательного функционала: [требования заказчика](../customer-requirements.md).
Этот документ фиксирует функциональные границы, согласованные при обсуждении первой версии.
Технические решения и план реализации определяются отдельно.

## Принятые решения

### Реальный рабочий цикл

Первая версия работает с реальным сотрудником и настоящими доступами GitHub.
Сотрудник проходит приглашение, подключает агента и готовит рабочее окружение.
После отключения сотрудника получение новых данных сотрудником и его агентом через платформу и GitHub должно блокироваться.
Цикл включает отзыв доступа к платформе и репозиториям GitHub.

### Одна компания и одна организация GitHub

Первая версия обслуживает одну компанию и одну организацию GitHub.
Внутри поддерживаются несколько сотрудников, проектов и репозиториев.
Поддержка нескольких компаний отложена.

### Условия пилота

В пилоте участвуют только выбранные закрытые репозитории.
Сотрудники получают доступ к ним через платформу.
У сотрудников пилота нет дополнительных прав через команды GitHub, базовые настройки организации или общие ключи доступа.
Роль владельца организации GitHub выходит за эту модель доступа.
Администратор перед пилотом приводит доступы выбранных репозиториев к этим условиям.
Автоматический перенос существующих схем доступа отложен.

### Прямое назначение проектов

Сотрудники получают проекты напрямую.
Команды и настраиваемые роли отложены.
Для работы с проектами предусмотрен один уровень доступа.

### Администратор и разработчик

Предусмотрены два фиксированных типа пользователей: администратор и разработчик.
Администратор приглашает сотрудников, создаёт проекты, назначает доступы и отключает сотрудников.
Разработчик работает с назначенными проектами.

Администратор управляет всеми проектами и назначениями.
Для получения инструкций и работы с репозиториями он назначает себе проект, как разработчику.
Агент администратора получает данные только назначенных ему проектов.

### Полномочия разработчика

Доступ к проекту разрешает читать код, отправлять изменения и создавать pull request во всех репозиториях проекта.
Этот доступ не включает управление настройками и удаление репозиториев.

### Общие репозитории

Один репозиторий может входить в несколько проектов.
Если сотрудник теряет доступ к одному проекту, доступ к общему репозиторию сохраняется через остальные назначенные проекты.
Доступ к репозиторию отзывается, когда у сотрудника больше нет проектов, которые его предоставляют.
При отключении сотрудника доступ отзывается ко всем репозиториям его проектов.

### Подключение и состав репозиториев проекта

Администратор добавляет в проект только существующие репозитории GitHub.
Создание, перенос и удаление самих репозиториев через платформу отложены.

После создания проекта администратор может добавлять и исключать репозитории.
Платформа автоматически пересчитывает доступы всех сотрудников проекта.
При добавлении репозитория сотрудники проекта получают к нему доступ.
При исключении репозитория доступ сохраняется только через другие назначенные проекты.

### Частичная выдача прав

Если доступ подтверждён не ко всем репозиториям проекта, успешные назначения сохраняются.
Платформа повторяет неуспешные операции и показывает администратору причину ошибки.
Назначение проекта сотруднику получает статус «Доступ настраивается».
Агент получает инструкции проекта после подтверждения доступа ко всем его репозиториям.
Частичная выдача прав не считается готовым подключением сотрудника к проекту.

### Поддерживаемый агент

В первой версии поддерживается только Codex.
Способ подключения к платформе ещё не выбран.

Через подключение к платформе Codex только читает доступные сотруднику проекты, репозитории и инструкции.
Приглашения, назначение прав и редактирование инструкций выполняет человек.
Инструменты управления платформой через агента отложены.

### Веб-интерфейс

В первой версии предусмотрен простой веб-интерфейс для администратора и разработчика.
Администратор управляет сотрудниками, проектами, инструкциями и доступами, видит ошибки GitHub.
Разработчик видит свои проекты, состояние доступов и порядок подключения Codex.
Отдельное приложение и административный интерфейс в командной строке отложены.

### Вход сотрудника

Администратор приглашает конкретный GitHub-аккаунт.
Сотрудник входит через GitHub и принимает приглашение.
Администратор получает ссылку на приглашение и сам передаёт её сотруднику.
Приглашение может принять только указанный GitHub-аккаунт.
Автоматическая отправка писем отложена.
Учётная запись платформы связана с GitHub-аккаунтом, который получает доступы к репозиториям.
Отдельные пароли платформы и восстановление пароля отложены.

### Локальное рабочее окружение

Codex готовит рабочее окружение на компьютере сотрудника.
Платформа предоставляет инструкции и управляет доступами.
Облачное окружение и запуск кода на стороне платформы отложены.

### Инструкции проекта

В платформе хранится один общий документ Markdown для каждого проекта.
Документ редактирует администратор с доступом к содержимому проекта.
Инструкции описывают подготовку рабочего окружения и проверку готовности.
Существующие инструкции в репозиториях сохраняются.
Синхронизация документов с GitHub, история версий и согласование изменений отложены.

### Готовность рабочего окружения

Подготовка считается успешной, когда агент скачал репозитории, установил зависимости и выполнил проверку из инструкций проекта.
Проверку определяют для конкретного проекта: например, запуск приложения или выполнение тестовой команды.
Если подготовка прервалась, агент сообщает причину и оставшиеся шаги.
Сотрудник получает результат подготовки в Codex.
Отдельная панель прогресса, централизованный сбор логов и мониторинг локального окружения отложены.

### Ошибка отзыва доступа

При отключении сотрудника платформа сразу блокирует его доступ и получение новых данных его агентом через платформу.
Если GitHub недоступен, отзыв прав в GitHub остаётся незавершённым.
Платформа показывает ошибку администратору и повторяет попытку отзыва.
Полное отключение подтверждается после успешного отзыва прав в GitHub.

### Профиль отключённого сотрудника

Профиль отключённого сотрудника сохраняется.
Вход в платформу и доступ его агента запрещены.
Администратор видит сотрудника и результат отзыва прав.
Полное удаление профиля отложено.

### Повторное подключение сотрудника

После полного отключения сотрудник может вернуться через новое приглашение.
Прежние права автоматически не восстанавливаются.
Администратор заново назначает проекты и полномочия.
Сотрудник заново подключает Codex.

### Неиспользуемые проекты

Архивирование и удаление проектов отложены.
Если проект больше не нужен, администратор снимает назначения сотрудников.
Описание проекта сохраняется.
Доступ к репозиториям отзывается с учётом других назначенных проектов.

### Граница отзыва доступа

Платформа прекращает получение новых данных сотрудником и его агентом через платформу и GitHub.
Уже скачанные репозитории и инструкции остаются на компьютере сотрудника.
Платформа не удаляет эти копии и не блокирует их локальную обработку.
Удаление корпоративных данных с компьютера остаётся отдельным процессом компании.

## Обязательные границы приложения

По требованиям заказчика подключение внешних сервисов выделяется в отдельный модуль интеграций.
Первой интеграцией будет GitHub.
Части приложения должны иметь понятные границы для дальнейшего развития платформы.
Конкретная архитектура ещё не выбрана.

## Развитие после первой версии

Все направления из раздела «Куда можем развивать платформу» требований заказчика отложены:

- Команды, дополнительные роли и управление доступами к другим инструментам.
- Общая библиотека скиллов, инструменты компании и контроль расходов на модели.
- Агент компании: сопровождение новичка, ответы по документации и подбор задач.
- Внешний или собственный трекер задач.
- Назначение задач агентам, облачные запуски, песочницы и параллельная работа агентов.
- Автоматизация проверок изменений, оценки агентов, релизов и эксплуатации сервисов.
- Обратная связь о работе агентов, наблюдение за ошибками сервисов и восстановление после сбоев.

Эта отсрочка не отменяет показ ошибок выдачи и отзыва прав GitHub, предусмотренный первой версией.
Опыт пилота определит следующие приоритеты.

## Вопросы следующего этапа

- Способ подключения Codex и его авторизации от имени сотрудника.
- Способ подключения GitHub и выполнения операций с правами.
- Начальная настройка интеграции и первого администратора.
- Порядок применения инструкций платформы и существующих инструкций репозиториев.
- Правила повторных попыток и проверки фактических прав в GitHub.
- Технологии приложения, размещение и план реализации.

Эти вопросы требуют отдельного проектирования. Документ не является готовым техническим планом.
