# Разрешённые зависимости предметных модулей

Для backend первой версии принят явный список разрешённых зависимостей. Зависимость означает использование интерфейса другого модуля. Доступ к внутренним деталям и чужим таблицам запрещён согласно [ADR-0007](0007-module-data-ownership.md).

| Вызывающий код | Разрешённые предметные модули |
| --- | --- |
| Прикладной сценарий | Любой из пяти модулей, необходимый сценарию. |
| Доступ | Сотрудники, Проекты, Интеграции. |
| Подключения агентов | Сотрудники. |
| Сотрудники | Ни один другой предметный модуль. |
| Проекты | Ни один другой предметный модуль. |
| Интеграции | Ни один другой предметный модуль. |

Предметные модули не вызывают прикладные сценарии. Все зависимости между перечисленными частями, которых нет в таблице, запрещены. Таблица описывает связи предметных модулей и прикладных сценариев; устройство общей технической инфраструктуры определяется отдельно.

«Доступ» получает состояние учётной записи и роль у «Сотрудников», состав проекта у «Проектов» и результат попытки сверки у «Интеграций». «Подключения агентов» используют состояние владельца подключения из «Сотрудников». Сквозные действия, включая отключение сотрудника, координируются прикладными сценариями согласно [ADR-0009](0009-application-scenarios.md).

Явный список сохраняет направленные зависимости и позволяет автоматически проверять импорты. Компромисс — необходимость координации действий через прикладные сценарии, когда прямой вызов между модулями запрещён. Для автоматической проверки импортов выбраны dependency-cruiser и ESLint: [ADR-0011](0011-module-dependency-checks.md). Схема сама по себе не обеспечивает атомарность изменений нескольких модулей и защиту от изменения прав во время запроса. Эти механизмы определяются отдельно.
