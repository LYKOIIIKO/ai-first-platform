# Dependency-cruiser и ESLint для проверки импортов

Для автоматической проверки зависимостей выбраны dependency-cruiser и базовое правило ESLint no-restricted-imports. Предусматривается запуск обоих инструментов локально и при проверке pull request в GitHub. Нарушения должны завершать соответствующую проверку с ошибкой.

Команда `pnpm check` объединяет проверку типов обоих приложений, ESLint, dependency-cruiser и проверку актуальности [HTTP-контракта и клиентских типов](0022-http-contract.md). CI запускает эту же команду на pull request. Для команды не нужны запущенные сервисы Compose.

Dependency-cruiser будет проверять полную матрицу из [ADR-0010](0010-allowed-module-dependencies.md), обращение только к согласованным интерфейсам модулей и отсутствие циклических импортов. Импорты типов подчиняются тем же ограничениям. Разрешение путей будет настроено по конфигурации TypeScript, чтобы проверка учитывала фактические файлы зависимостей.

Обычный межмодульный код использует `public.ts`. Импорт `*.module.ts` допускается в коде сборки NestJS. Приёмка проверяет оба случая и запрет импорта внутреннего файла через `import type` и псевдоним.

Предметный код не импортирует NestJS, Drizzle, клиент RabbitMQ и транспорт. Эта проверка добавляется вместе с первым кодом предметных правил.

ESLint будет давать раннюю обратную связь при редактировании файла. В нём будут заданы простые ограничения импортов, включая обращения к внутренним файлам чужих модулей. Полная матрица зависимостей не должна дублироваться вручную в двух конфигурациях. Частичное пересечение проверок допустимо.

Сообщение архитектурной проверки показывает запрещённый импорт и нарушенное правило. Если правило допускает другую точку входа, сообщение подсказывает её. Например, для допустимого межмодульного вызова используется `public.ts`. [Точки входа модулей](0013-backend-layout.md).

Рассмотрено использование только одного инструмента. Выбрана комбинация быстрой проверки отдельного файла и анализа общей схемы зависимостей. Компромисс — две конфигурации. Проверка импортов не доказывает корректность авторизации, транзакций или произвольного SQL. Эти свойства требуют проверки кода и поведения.

Решение фиксирует выбор инструментов. Установка, конфигурация и подключение проверок в GitHub выполняются после согласования структуры каталогов и точек входа модулей.
