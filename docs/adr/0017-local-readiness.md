# Проверки готовности локального окружения

Для готовности локального окружения предусмотрены отдельные проверки. Сервис db будет использовать pg_isready, чтобы подтвердить приём соединений PostgreSQL. RabbitMQ использует собственную проверку готовности в Compose. Backend предоставляет /health/live для проверки процесса. /health/ready выполняет SELECT 1 и проверяет открытие AMQP-канала через соединения API с настроенными учётными данными. Ответ показывает состояние PostgreSQL и RabbitMQ отдельно. Web будет проверяться HTTP-запросом к странице Vite.

Одного pg_isready недостаточно для проверки соединения backend: состояние сервера можно получить и с неверными учётными данными. Настоящий запрос из api будет проверять адрес, учётные данные и выполнение SQL. Если база или брокер недоступны либо проверка превышает свой таймаут, /health/ready возвращает HTTP 503. Таймаут БД включает получение соединения и выполнение SELECT 1. Таймаут RabbitMQ включает соединение и открытие канала. Значения приводятся в корневом README.md. После остановки и восстановления зависимости готовность меняется без ручного перезапуска API.

Compose должен дожидаться готовности db и rabbitmq перед запуском api. Web должен запускаться независимо от api, чтобы интерфейс можно было открыть при недоступном backend. Общая команда проверяет ответ страницы web и запрашивает /api/health/ready по адресу web через прокси Vite. Это позволяет обнаружить и сбой прокси, и неготовность API, базы или брокера. Отрисовка React и обращение интерфейса к backend подлежат дополнительной проверке в браузере.

В браузере используется техническая страница `/system`. Она вызывает тот же endpoint через типизированный клиент и показывает состояние каждой зависимости. Ответ HTTP 503 с результатами проверок и отсутствие ответа API отображаются как разные состояния. [HTTP-контракт](0022-http-contract.md).

Для всех четырёх сервисов задаются проверки готовности Compose. Проверка web обращается к его странице, а проверка API — к `/health/ready`. `pnpm smoke` запускает полный стек с помощью `docker compose up --wait` с конечным `--wait-timeout`. Затем он вызывает общую команду готовности. При ошибке запуска, истечении таймаута или неуспешной HTTP-проверке команда возвращает ошибку. Общая команда также работает отдельно для уже запущенного окружения.

GitHub не включается в общую проверку готовности. При его сбое платформа должна оставаться доступной для показа ошибок и повторных сверок. Проверка SELECT 1 подтверждает соединение с базой. Проверка AMQP-канала подтверждает доступность брокера для API. Приёмка доставки событий появится с первым предметным событием.

Рассмотрена проверка только запущенных процессов. Выбраны раздельные проверки процесса и соединений с зависимостями, чтобы различать причины неготовности. Компромисс — дополнительные технические обработчики и команда проверки. Они относятся к окружению, а не к пользовательским функциям. Пока обработчики и команда не реализованы; готовность сервисов не проверена.

Источники: [pg_isready](https://www.postgresql.org/docs/current/app-pg-isready.html), [порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/).
